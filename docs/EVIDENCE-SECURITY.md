# Evidence trust and credential handling

## Optional evidence signatures

Unsigned verification checks structural consistency and, for replay-backed reports, the stored digests and event logs. An attacker who can replace the entire unsigned set can create another consistent set. The word "verified" alone does not imply authenticity.

After finalization, explicitly seal evidence using an independently provisioned Ed25519 private key:

```sh
abb sessions sign latest --private-key /secure/abb-signing.pem
abb sessions verify --trusted-key /trusted/abb-verification.pem --json
```

The signing CLI requires encrypted PKCS8 PEM and reads its passphrase from `ABB_SIGNING_PASSPHRASE` (or the variable named by `--passphrase-env`). Supply it through a protected process environment or secret manager; never put a passphrase in command arguments, repository configuration, evidence, or shell history. Verification requires SPKI public PEM. Both key paths must resolve outside the repository and session storage, and final-component symlinks are refused. On POSIX, private files must have no group/other permissions and public keys must not be group/other writable. Windows ACLs are not inspected: provision and protect keys using appropriate Windows ACLs. Location and encryption do not establish independent trust by themselves.

Keep the signing key, passphrase, and signing process under a separate principal or trusted signing host that evidence writers cannot control. Pin the public key through an authenticated channel into storage/configuration that evidence writers cannot change. Confirm its SHA-256 SPKI fingerprint through that channel; the signing command prints the fingerprint. The CLI neither generates keys automatically nor accepts a public key from the evidence. It does not store private keys or passphrases. Programmatic callers can supply existing Node `KeyObject` values to `signSessionEvidence` and `verifySessions(entries, { trustedKey })`; they are responsible for protecting and independently trusting those keys.

The detached `evidence-signature.json` binds the exact session ID, raw bytes and lengths of `session.json`, `session-start.json`, `git-start.json`, `events.ndjson`, `commands.ndjson`, and `session-replay.json`, including absence of optional files. SHA-256 digests are signed with Ed25519 using a versioned, domain-separated payload. Signing streams files with existing format limits (raw logs: 1 GiB each) and refuses to replace an existing seal. Archives retain the seal and can be verified with the same trusted key after relocation.

With `--trusted-key`, every selected session must have a valid matching signature and pass ordinary structural verification. Missing, altered, unsigned, wrong-key, or incomplete evidence fails; JSON adds `signatureVerified: true` and `keyFingerprint` only on success. Omitting the key preserves existing unsigned verification behavior and does not authenticate a present signature. Use an explicit session ID for security decisions: catalog ordering and `latest` are not authenticated. Derived Markdown, metadata/search indexes, capture markers, other files, and reports exported without the seal are outside the signature's scope. Use `--check-indexes` or `--repair-indexes` for derived indexes; those operations do not invalidate a seal.

A valid seal proves only that the signed bytes match what the holder of the independently trusted private key signed. It does not prove the recorded commands ran, capture was complete, source content was true, or evidence was intact before signing. It provides no trusted timestamp, revocation service, freshness, anti-replay guarantee, or inventory of deleted sessions. Retain expected IDs/seals outside attacker-controlled storage when deletion or replay matters. File checks detect many mutations but do not provide an atomic filesystem snapshot against concurrent writers; sign/verify quiescent copies in trusted storage. Compromised signing keys must be retired through the same independent trust channel. If an attacker controls both evidence and its trust anchor, verification provides **no authenticity guarantee**.

## Credential detection and resource limits

Built-in detection and command redaction share provider token shapes, recognize Basic/Bearer authorization headers, URL userinfo credentials, private-key headers, and selected escaped JSON assignment names. Added shapes include AWS temporary IDs, GitHub fine-grained tokens, GitLab, npm, and PyPI tokens. Provider formats can change or use custom prefixes; findings remain **possible** credentials and no online credential validation is performed. For example, [AWS documents the ASIA prefix](https://docs.aws.amazon.com/STS/latest/APIReference/API_GetAccessKeyInfo.html), [GitHub documents github_pat_](https://docs.github.com/en/authentication/keeping-your-account-and-data-secure/about-authentication-to-github), and [GitLab permits custom token prefixes](https://docs.gitlab.com/administration/settings/account_and_limit_settings/).

JWT and LLM token processing avoids retrying greedy suffixes at every repeated prefix. Known-token redaction accepts at most 65,536 UTF-16 code units; larger inputs are entirely redacted. Command arguments over 4,352 code units and oversized command metadata are entirely redacted before parsing. Executed command arguments are unchanged. File scanning retains the existing file-size, path, binary-file, line-number, allowlist, and finding-redaction controls.

Custom regexes retain their syntax, validation, 32-pattern/256-character limits, and leading 4,096-character line scan limit. File scans group up to 64 independent line prefixes and 65,536 total UTF-16 code units in each worker message; regexes are compiled once for that message and retain their per-line matching semantics. No matches are discarded to fit the batch. Execution happens in a reusable worker with the same 500 ms deadline for the entire evaluation batch, 5 s startup deadline, 32 MiB old-generation/8 MiB young-generation heap limits, 2 MiB stack, 65,536-character redaction input limit, 131,072-character intermediate output limit, and 1 MiB result buffer. These are worker/input bounds, not a total process RSS cap or hard real-time scheduling guarantee. Timed-out workers are terminated. Scanning throws an explicit incomplete-scan error; redaction hides the entire input. A rules object that times out remains failed for its lifetime, preventing repeated retries of the same expensive patterns. A new compilation may retry; many rules objects/files still entail aggregate work. Existing allowlists suppress detection findings only, never command redaction.

A longer line remains fully available to built-in detectors, but its custom-pattern scan is incomplete. Analysis adds an `analysis-limit` finding and structured `coverage.limited` entries; baseline comparisons retain their own limited paths. `complete-review` and configured `requireCompleteCoverage` gates fail for either staged or needed baseline partial scans. `new-secrets` still gates detected new secrets only and retains the diagnostics. Finalized recorded sessions include these limits as integrity warnings. Allowlisting detected credentials cannot hide an incomplete scan, and limit diagnostics never contain line content or skipped credential values.

Detection is still heuristic: unknown, short, encoded, split, obfuscated, or context-dependent credentials may be missed; examples and non-secret identifiers can trigger findings. Only the configured leading line portion is scanned for custom patterns, and file-size/analysis budgets can skip content. Private key bodies without a recognized header may be missed. Review reports before sharing, minimize recorded sensitive inputs, and use a dedicated secret-scanning workflow for additional coverage. Redaction and signatures do not turn command execution into a sandbox.
